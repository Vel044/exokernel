# 驱动迁移首次会议提纲

建议时长 45–60 分钟。会议目标：让对方知道这套内核如何承载驱动，并共同确定 Linux → IR 的一个可验收小任务。

## 开场可以这样说（约 2 分钟）

> 我这边已经有一套 AArch64 外核原型。内核管理资源授权、地址空间和中断投递，设备协议主要放在用户态。已有 UART、xHCI 上的 USB 串口和 UVC，以及 virtio-blk 上的 ext4 读取路径。我们今天先用 UART 看接口，再用 DMA 看迁移时必须保留的语义，最后确定你这边做 Linux 到 IR 的第一个样例。目标代码暂时不定，但前端需要明确哪些信息不能丢。

## 讲解顺序

| 时间 | 内容 | 打开的材料 | 要达到的理解 |
| --- | --- | --- | --- |
| 0–5 分钟 | 对齐任务 | [协作入口](README.md) | IR 第一阶段只做什么，DMA 指哪一类问题 |
| 5–12 分钟 | 结构与边界 | [根 README](../../README.md) | EL1 保护资源，EL0 实现协议；现有 Rust 适配并非 Linux 自动翻译结果 |
| 12–22 分钟 | UART 小例子 | `uart_echo.rs::run`、`sys_map_mmio`、IRQ 入口 | MMIO 授权后直接访问；Notification、设备清中断、EOI、ACK 各做什么 |
| 22–35 分钟 | DMA 主线 | `dma.rs`、`sys_dma_alloc/free` | CPU VA / DMA address、页与所有权、同步与回收 |
| 35–45 分钟 | Linux 对照 | Linux `xhci-mem.c::xhci_alloc_erst` | 源侧哪些语义要进入 IR，哪些暂时不能映射 |
| 45–60 分钟 | 定范围和分工 | 下方待明确问题 | 一个样例、一组输出、一个验收日期与待解决问题 |

如果只有半小时：结构 5 分钟、UART 5 分钟、DMA 10 分钟、IR 范围和分工 10 分钟。ACT、完整 UVC 和调度器内部算法先不展开。

## 现场画两张简单图

```text
UART：输入 → 设备 IRQ → GIC → EL1 屏蔽/EOI/通知
     → EL0 读写 FIFO → 清设备中断 → IRQ_ACK

DMA：CPU --VA--> buffer <--DMA address-- 设备
     分配 → 初始化/同步 → 设备使用 → 确认完成 → 回收
```

强调 UART 不含 DMA；DMA address=PA 只适用于当前无 IOMMU 的实现条件。

## 必须在会上明确的问题

1. “DMA”是研究设备 DMA 内存管理，还是 DMAengine 驱动？
2. IR 准备用来分析依赖、检查生命周期，还是未来自动生成驱动？近期优先哪一种？
3. 先输出 LLVM IR，还是同时附加驱动语义？遇到未知调用如何报告？
4. Linux 输入来自哪个仓库、commit、架构和配置？首例是否选 `xhci_alloc_erst`？
5. 第一轮成功是否定义为“复现解析 + 资源/错误路径标注”，明确暂不要求设备运行？
6. 对方何时交首例，你何时提供人工对照，下一次什么时候共同核对？

## 会前准备

- 将仓库主线链接和入口文档发给对方，直接 fork 默认的 main 分支。
- 说明独立构建还缺少同级 `rutorch` 源码；本轮源码/IR 工作可先开始，不承诺仅 fork 即可运行内核。
- 预先打开 `abi/src/lib.rs`、`uart_echo.rs`、`dma.rs`、`dispatch.rs` 四个文件，用函数名定位，避免从入口开始逐行讲全内核。
- 有时间则准备 UART 回显演示；没有当日实测结果时直接走读代码，不把历史日志说成现场验证。
- Linux/Windows 端只说明需安装 AArch64 QEMU、Rust 目标和 UEFI 固件，并调整启动盘/固件路径与宿主脚本。本次不做这些适配；QEMU virt 接口可对照理解，现有 macOS 脚本不保证原样通用。
