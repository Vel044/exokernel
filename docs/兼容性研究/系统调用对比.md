# Linux 与 exokernel 系统调用对比

## 对比口径

Linux 使用 v6.12 AArch64 原生表：318 个具名编号，最大编号 462；`__NR_syscalls = 463` 是编号空间上界，包含空洞，不能称为“463 个已实现 syscall”。编号 18、42 在表中显式为 `sys_ni_syscall`；其他条目也可能因架构或配置而不可用。[上游表](https://github.com/torvalds/linux/blob/v6.12/scripts/syscall.tbl)

exokernel 依据当前 [ABI 定义](../../abi/src/lib.rs) 和 [EL1 分发器](../../kernel/src/syscall/dispatch.rs)，共 37 个 syscall，均找到对应分发分支。这是接口覆盖核查，不是运行正确性证明。

两者都可以使用 AArch64 的 `x8` 和 `svc #0`，但**编号及语义不同**。例如 Linux 的 29 是 `ioctl`，本项目的 29 是 `SYS_NOTIFICATION_SIGNAL`。不能把未经处理的 Linux SVC 直接交给当前分发器。

## exokernel 完整清单

参数是逻辑意义，精确 ABI 以源码为准。IPC 消息通过线程固定 IPC Buffer 传递，不能只看寄存器参数推断消息内容。

| 编号 | 调用 | 输入及作用 | 结果 / Linux 对照限制 |
| --- | --- | --- | --- |
| 2 | `SYS_PUTS` | 用户字符串 VA、长度；输出调试信息 | 不是带 fd、返回实际字节数的 `write` |
| 5 | `SYS_EXIT` | 退出码；结束当前 EL0 task 并清理资源 | 当前实现包含停其他 CPU 等任务级清理，不是 POSIX 子进程 `exit` |
| 6 | `SYS_MAP_MMIO` | PA、size、VA；校验 grant 后建立设备映射 | 成功为 0；更接近驱动 `ioremap` 的底层机制 |
| 7 | `SYS_IRQ_BIND` | INTID、Notification handle、badge、目标 CPU | 校验授权后绑定 IRQ，不直接接收 Linux C 中断回调 |
| 9 | `SYS_IRQ_ACK` | INTID；重新开放先前屏蔽的 IRQ | 不负责清设备状态，也不是 Linux `read` |
| 10 | `SYS_IRQ_UNBIND` | INTID；解除绑定 | 必须安排设备停机及处理者生命周期 |
| 11 | `SYS_UNMAP_MMIO` | VA、size；撤销已登记映射 | 校验所有权与映射范围 |
| 12 | `SYS_DMA_ALLOC` | size、alignment、指定 EL0 VA | 连续清零物理页、非缓存映射；当前返回 PA 作为 DMA address |
| 13 | `SYS_DMA_FREE` | VA、size | 核对所有权后解除映射和回收；调用前设备必须停止使用 |
| 14 | `SYS_FRAME_ALLOC` | 页数、页对齐要求 | 返回 Frame handle，不是用户 VA |
| 15 | `SYS_FRAME_FREE` | Frame handle | 释放内存对象；与撤销映射分开 |
| 16 | `SYS_FRAME_MAP` | Frame、页偏移、页数、VA、权限 | 返回当前 VSpace 的 Mapping handle |
| 17 | `SYS_FRAME_UNMAP` | Mapping handle | 撤销映射，不等同于 Linux 任意区间 `munmap` |
| 18 | `SYS_THREAD_CREATE` | 入口、参数、CPU、优先级、优先级授权上限 | 创建当前地址空间线程；不是完整 pthread/clone |
| 19 | `SYS_THREAD_EXIT` | 退出码 | 结束当前线程；无可切换线程时进入 task 退出路径 |
| 20 | `SYS_THREAD_YIELD` | 无 | 让出执行机会；可作为 `sched_yield` 后端候选 |
| 21 | `SYS_THREAD_SET_PRIORITY` | Thread handle、优先级 | 有授权上限；需转换 POSIX 策略及优先级含义 |
| 22 | `SYS_ENDPOINT_CREATE` | 无 | 创建同步 IPC Endpoint |
| 23 | `SYS_ENDPOINT_SEND` | Endpoint handle，数据在 IPC Buffer | 同步发送，可阻塞；不是 socket send |
| 24 | `SYS_ENDPOINT_RECV` | Endpoint handle | 同步接收，可阻塞 |
| 25 | `SYS_ENDPOINT_CALL` | Endpoint handle | 请求并等待 Reply |
| 26 | `SYS_ENDPOINT_REPLY` | Reply handle | 对先前请求回复 |
| 27 | `SYS_ENDPOINT_REPLY_RECV` | Endpoint handle、Reply handle | 回复并接收下一请求 |
| 28 | `SYS_NOTIFICATION_CREATE` | 无 | 创建异步通知对象 |
| 29 | `SYS_NOTIFICATION_SIGNAL` | Notification handle、badge | 合并 pending 位图；不是计数信号量 |
| 30 | `SYS_NOTIFICATION_WAIT` | Notification handle | 取走 pending badge；为空才阻塞当前线程 |
| 31 | `SYS_NOTIFICATION_POLL` | Notification handle | 非阻塞取走 pending；为空返回 SYS_ERR_WOULD_BLOCK（以 EL1 实现为准） |
| 32 | `SYS_NOTIFICATION_DESTROY` | Notification handle | 活跃绑定/等待可能阻止销毁 |
| 33 | `SYS_THREAD_RUNTIME` | Thread handle | 返回运行 tick；不是实时时钟或完整 `clock_gettime` |
| 34 | `SYS_ENDPOINT_DESTROY` | Endpoint handle | 销毁空闲 IPC 对象 |
| 35 | `SYS_VSPACE_CREATE` | 无 | 创建地址空间；不是 fork |
| 36 | `SYS_VSPACE_DESTROY` | VSpace handle | 销毁地址空间，检查忙状态 |
| 37 | `SYS_FRAME_MAP_TO` | Frame、目标 VSpace、偏移、页数、VA、权限 | 向指定地址空间建立映射 |
| 38 | `SYS_THREAD_CREATE_IN` | VSpace、用户 ThreadCreateConfig 指针 | 复制并校验配置，创建 Suspended 线程 |
| 39 | `SYS_THREAD_START` | Thread handle | 启动挂起线程 |
| 40 | `SYS_THREAD_SUSPEND` | Thread handle | 挂起线程，不等同于 POSIX signal |
| 41 | `SYS_THREAD_DESTROY` | Thread handle | 销毁符合状态要求的线程 |

## Linux 常用接口如何对应

以下“可组合”表示设计可能性，并非当前已实现兼容。完整 Linux 编号另见 [清单](Linux系统调用完整清单.md)。

| Linux ARM64 syscall | 当前已有机制 | 还需补充的语义 / 位置 |
| --- | --- | --- |
| `read(63)`、`write(64)`、`readv(65)`、`writev(66)` | UART、USB transport 和 ext4 读取在 EL0 | libOS 建 fd 表、访问模式、偏移、短读写、阻塞/非阻塞与 errno；不是直接映射为 SYS_PUTS |
| `openat(56)`、`close(57)` | ext4 路径读取、驱动对象 | libOS 建 VFS、路径基准、打开文件对象及引用计数；设备节点可为虚拟路径 |
| `lseek(62)`、`newfstatat(79)`、`fstat(80)`、`statx(291)` | 可从文件后端获取部分信息 | 文件偏移、metadata、结构布局；串口 seek 返回 ESPIPE 等 |
| `getdents64(61)`、`mkdirat(34)`、`unlinkat(35)` | 没有通用 POSIX 目录层 | 目录迭代及写入语义；首阶段只读，写操作明确 EROFS |
| `ioctl(29)`、`fcntl(25)` | 各驱动自有配置接口 | 按具体设备请求实现；tty/termios 单独定义支持子集，不能全部返回成功 |
| `dup(23)`、`dup3(24)`、`pipe2(59)` | 内存、同步 IPC/Notification | fd 引用关系、共享 offset、管道字节流及生命周期 |
| `brk(214)`、`mmap(222)`、`munmap(215)` | Frame + Mapping + VSpace | libOS VA 管理；匿名映射可优先做，文件映射、部分解除、共享语义另做 |
| `mprotect(226)`、`mremap(216)` | 有映射权限，无同名原语 | 在并发条件下变更映射的原子性和回滚；不能仅包装已有 unmap/map 就声称等价 |
| `clone(220)`、`clone3(435)` | Thread、VSpace、EL0 ProcessBuilder | flags、TLS、父子关系、共享资源和退出通知；不能视为一对一 |
| `execve(221)`、`wait4(260)`、`waitid(95)` | 可装载简单 AArch64 ELF 的 PT_LOAD | argv/envp/auxv、TLS、装载约定、进程替换、子进程状态；动态链接器另做 |
| `exit(93)`、`exit_group(94)` | Thread/Task 退出 | 线程组、资源归属、可等待的退出状态；现有 SYS_EXIT 粒度不匹配 |
| `futex(98)`、`futex_waitv(449)` | Notification + 线程阻塞 | 比较内存值与入队的原子性、等待者队列、超时、共享映射；不等同于 Notification |
| `sched_yield(124)`、`sched_setscheduler(119)` | Thread yield/priority | 先支持明确策略子集；Linux 的策略及数值不能直接套用 |
| `clock_gettime(113)` | EL0 可读 cntvct/cntfrq | 可构造单调时间；CLOCK_REALTIME、其他 clock ID 需另定 |
| `nanosleep(101)`、`clock_nanosleep(115)` | 当前 delay_ns 为计数器忙等 | 定时唤醒服务/原语、超时与中断处理；忙等不应冒充完成的阻塞实现 |
| `ppoll(73)`、`epoll_create1(20)`、`epoll_ctl(21)`、`epoll_pwait(22)` | Notification 单对象事件位图 | 多 fd readiness、注册/取消、超时、边沿/水平触发及竞态处理 |
| `rt_sigaction(134)`、`rt_sigprocmask(135)`、`rt_sigreturn(139)` | 没有对应完整模型 | 信号掩码、信号帧、上下文保存恢复；不能把 badge 当 signal |
| `socket(198)`、`bind(200)`、`connect(203)`、`sendto(206)`、`recvfrom(207)` | Endpoint 是 IPC 原语 | 网络设备、协议栈、socket fd 和协议语义；本次未发现通用 socket 层 |
| `getrandom(278)` | 未发现对应接口 | 熵源、初始化和阻塞语义；普通伪随机不能替代 |
| `mount(40)`、BPF、namespace、io_uring、LSM 等 | 无对应兼容层 | 不列入近期嵌入式应用子集 |

## 直接影响方案的源码事实

- [runtime](../../libos/src/runtime/mod.rs) 既有 SVC 薄封装，也有输出、计数器和忙等工具；[kernel_api](../../libos/src/kernel_api/mod.rs) 在其上提供 Frame、Thread、Notification 等对象接口。两者目前不是 POSIX libc。
- [fs/ext4.rs](../../libos/src/fs/ext4.rs) 提供读取映射；[fs/capture.rs](../../libos/src/fs/capture.rs) 只覆盖宿主预分配文件的数据区，不更新目录、inode、位图或 journal。不能把捕获功能宣传为通用可写 ext4。
- [ProcessBuilder](../../libos/src/kernel_api/process.rs) 已组合地址空间、映射、栈及线程；当前构建空栈，没有准备 Linux argv/envp/auxv 启动栈。拥有 ELF 装载不代表能执行普通 Linux ELF。
- [Notification](../../libos/src/kernel_api/notification.rs) 是合并位图，需要另建条件/计数/队列状态。它可唤醒执行器或工作线程，但不直接提供全部 Linux futex、poll、signal 语义。
- 本地对象接口使用 `u64::MAX` 至 `u64::MAX-7` 的自定义错误集合；MMIO、DMA_FREE 及部分 IRQ 接口仍使用正整数错误，DMA_ALLOC 用 `u64::MAX` 表示失败。Linux ABI 错误是对应负 errno；libc 通常再转换为 `-1` 并设置线程局部 errno。兼容层必须按操作翻译，不能透传；未知 syscall 应按目标 ABI 返回 ENOSYS，而当前原生 dispatcher 返回自定义 INVALID。

## 应用兼容时一次 read 的拟议路径

```text
C 应用 read(fd, buffer, size)
  → 移植后的 libc / POSIX 层
  → libOS fd 表找到串口设备对象
  → UART 或 USB transport
  → 有数据：复制并返回实际字节数
  → 无数据且阻塞模式：通过执行器/驱动工作线程等待 Notification
       → SYS_NOTIFICATION_WAIT → EL1 调度其他线程
       → IRQ 到达 → EL0 处理设备事件 → SYS_IRQ_ACK
       → read 返回
```

具体阻塞桥接需要设计：现有 USB read 是 Rust Future，而 C read 是同步入口。可由常驻 USB 工作线程维护收发队列，C 线程通过请求队列与通知等待结果。避免每个 C 调用都争用同一个 xHCI EventHandler。完成数据放在队列中，Notification 只提示“状态可能变化”，唤醒后重新检查条件。

应用看见 POSIX read，不要求 EL1 新增一个懂 USB 的 Linux read syscall。若要接受未修改 Linux 二进制中写死的 `svc #0`，则必须另外实现 Linux ABI 分流及服务机制。
