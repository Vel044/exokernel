# LiteEth AI 定向翻译实验汇报

2026 年 10 月 23 日

AI 辅助将 Linux LiteEth 驱动定向重写为直接使用 exokernel 接口的 Rust 驱动，已在所附 ARM64 QEMU 模型中跑通。原始 C 文件保留不变，两个版本通过相同的应用和测试输入，对比帧内容、统计、收发槽和启停顺序；Rust 产物未链接 C 兼容层。

## 研究目标

减少单个驱动迁移时需要携带的 Linux 依赖。AI 识别驱动真正需要的设备行为，将操作系统相关功能改写为目标系统已有能力，并删除当前功能范围内不需要的框架依赖。

本次目标是单设备、单所属 EL0 线程的完整以太网帧收发。通用 Linux 兼容、ARP/IP/socket、PHY 管理和真实 FPGA 验收不在本次实验范围内。

## 本次实际过程

本次没有严格执行“先固定解释和依赖替换清单，再仅依据清单生成代码”的阶段流程。实际过程如下；下面的顺序不能用事后补齐的文档追认为事前约束。

**阅读输入和已有定位。** 使用 Linux 6.12.75 的 `litex_liteeth.c`，结合此前保存的文件哈希、9 个驱动函数和 49 个直接外部函数或宏名称清单阅读源码及相关依赖。49 是直接名字的词法清单，不是递归依赖数量。原文件完整保留，C 对照通过此前的窄兼容层运行。生成 Rust 之前，没有先单独交付一份覆盖所有依赖、包含未知项的完整解释文档。

**在会话分析中决定替换并编写代码。** AI 在分析源码时确定硬件顺序、所有权和接口替换方式，随即编写 Rust 状态机和内核接口接入代码。这些决定没有先固定为独立、完整、带版本的结构化契约；代码也不是由一个读取该契约的生成工具产生。只有 MMIO 和屏障边界使用 `unsafe`，状态机使用切片、值类型和有界数组。

**构建和测试。** 共用回显应用，分别构建 C 与 Rust。QEMU 外部输入帧相同，比较返回字节、统计、slot/长度、SLOT/LENGTH/START 顺序和事件启停。另检查超长 TX 丢弃、映射失败回滚及部分生命周期错误。忙状态由模型的异步完成机制触发，并非对两个版本逐事件重放相同时间表。非法 RX slot/长度等只在 Rust 宿主测试中检查，没有全部构造成两版本相同的异常输入对照。

**事后整理契约与汇报。** 对照测试通过后，才把各项依赖替换、源码位置、保留规则和主动改变的边界汇总到 [翻译契约](翻译契约.json)。该文件可用于检查当前实现，但不能作为本次“先契约后生成”的证据。原始定位见 [源码核查](源码核查.json)。

因此，这次属于 AI 辅助定向重写和测试验证的探索样例。若要验证用户提出的分阶段方法，下一轮应先完成原驱动解释与未知项记录，再固定依赖替换清单和行为规则，然后生成实现；测试失败时分别记录实现错误、契约缺项及契约修订。现有运行成功的结果不等同于已经验证了这套分阶段流程。

## 依赖如何减少

| Linux 依赖 | Rust 目标实现 |
| --- | --- |
| `platform_device`、`net_device`、私有数据指针 | EL0 已解析的 `LiteEthInfo` 与驱动字段 |
| `devm_*` 资源托管 | 拥有映射、通知的 Rust 对象及 Drop，失败时回滚 |
| `ioremap` | 已有 `MAP_MMIO/UNMAP_MMIO`，EL1 继续审核授权 |
| `litex_read/write`、`memcpy_toio/fromio` | CSR32、LE、volatile 和 ARM `dmb osh`，保持设备访问顺序 |
| `request_irq/free_irq` | 已有 Notification 与 IRQ 绑定/解绑；EL0 主动处理设备事件后 ACK |
| `sk_buff` 分配和释放 | 有界接收副本与借用的发送切片，数据路径没有每包堆分配 |
| `netif_rx`、发送队列、统计 | 完整帧交付槽、驱动状态和统计值；不引入 Linux 网络调度框架 |
| 模块注册、Linux 链路通知和协议分类 | 当前应用直接管理驱动生命周期；完整帧由上层解释 |

没有为 Rust 版本新增 syscall，也没有将网络协议或驱动逻辑移入 EL1。LiteEth 使用设备 SRAM 复制，本次不涉及 DMA。

MAC 自动生成和 Linux 链路发布没有纳入目标接口：本实验由上层提供完整 L2 帧，原文件也没有通过这些 API 设置硬件 MAC 寄存器。这是明确限定功能范围后移除的策略，不能据此宣称所有原 Linux 网络接口均已保持。

## 实测结果

| 检查项 | C 对照 | 原生 Rust |
| --- | --- | --- |
| 外部逐字节回显 | 17 帧，共 10,752 字节 | 相同 |
| 测试帧长度 | 18、60、64、127、512、1024、1514、2048 字节 | 相同 |
| RX/TX slot 及长度 | 17 次收、17 次发，双槽轮转 | 相同 |
| 发送寄存器顺序 | SLOT → LENGTH → START | 相同 |
| 超长发送 | 2049 字节被消费但不发送；TX 错误与丢弃各增加 1 | 相同 |
| 最终统计 | RX/TX 各 17 包、10,752 字节，RX 错误 0，TX 错误/丢弃各 1 | 相同 |
| 资源与状态 | 未授权第一/第二段映射失败回滚；拒绝重复 attach/open 和关闭时发送；停止、重开、解绑、再探测 | 通过相同检查 |
| 链接 C 兼容层符号 | 有 | 无 |
| 当前测试 libOS ELF 文件大小 | 152,472 字节 | 146,568 字节 |

ELF 大小包含公共运行时和测试应用，不是单个驱动大小，也不是运行性能指标。完整机器可读结果见 [对照测试摘要](对照测试摘要.json)。本机原始日志、设备 trace、ELF 和符号表位于 `target/liteeth-comparison/20261023-120009/`，生成物不提交。

Rust 实际状态机通过 11 项宿主测试，覆盖忙时所有权、提交顺序、IRQ 次序、非法 slot/长度、缓冲不足、交付槽满及启停状态。C 兼容版本的 ASan/UBSan 测试也通过。既有的进程地址空间与固件 DTB 两项回归通过，报告位于 `target/dtb-regression/20261023-120328/`。宿主数组测试不替代真实 MMIO/IRQ 检查，两版本均另外在 ARM64 exokernel 中运行。

## 安全边界与结论

Rust 版本主动加强了设备输入检查：遇到越界 RX slot、超容量长度和不足 14 字节的帧，先拒绝再确认设备事件，避免按不可信偏移读取 SRAM。原 C 文件没有完整检查 slot；此前 C 适配层会在部分越界情况下终止任务。因此异常输入路径并非逐项等价，差异已在契约中列明，不能把安全收紧隐藏成“翻译完全相同”。

当前证据支持：**在明确功能范围内，AI 可以将一个 Linux 驱动改写为直接使用目标内核接口的 Rust 驱动，消除该样例对 Linux 风格兼容 API 的运行依赖，并通过所附模型上的对照验收。** 这为后续自动化提供了可检查的步骤和测试入口。

目前没有测量人工移植工时或吞吐/延迟，也没有形式化证明；不能据此量化“效率提升”或宣称整体安全性已经得到证明。已确认的变化是依赖边界减少、数据路径取消每包分配，以及设备输入检查更明确。下一项实验应在第二个驱动上验证这种方法是否可重复，并记录人工修订量和翻译失败类型。

## 会议口述稿

我们这次尝试让 AI 迁移一个具体驱动。先分析 Linux LiteEth 需要保留的硬件操作和资源规则，在会话分析中决定替换方式并编写直接运行在 EL0 的 Rust 驱动；结构化契约是在测试后补齐的。原 C 驱动保留作对照。两版在相同 QEMU 模型上完成了 17 帧逐字节收发对比，统计、收发槽及启停顺序一致，Rust 版本也没有链接原来的 C 兼容层。这说明这个样例可以通过定向翻译减少依赖；后续还需要第二个样例和真实硬件，验证方法的可重复性，并测量实际节省的人工工作。
