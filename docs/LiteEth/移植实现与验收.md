# LiteEth 移植实现与验收

> 此页保留早期实验记录。2026-10-26 逐函数整改后的接口、测试及剩余差距以 [整改结果](逐函数翻译整改结果.md) 为准。

本文主要记录原 C 对照版本。当前 Rust 版本新增可复用的 [Linux 同名接口层](Linux同名接口.md)，两版仍独立构建并对照测试。

## 这次移植的对象

将 Linux 6.12.75 的 `drivers/net/ethernet/litex/litex_liteeth.c` 原样编译为 AArch64 C 对象，静态链接到 EL0 libOS。保留原驱动的 probe、open、stop、start_xmit、interrupt、get_stats64、remove，不通过 IR 重写这些函数。

第一方兼容层位于 `libos/src/drivers/linux_liteeth/`；原文件和版权位于 `libos/vendor/liteeth-linux/`。这里只实现该文件实际需要的内核内部 API 子集，不提供 Linux 内核 ABI、模块动态加载、POSIX 或 socket 兼容。

## 实际调用链

```text
apps::run → liteeth_smoke::run
  → Driver::liteeth_probe → 原 liteeth_probe
  → Driver::liteeth_open → 原 liteeth_open → request_irq
  → Notification::wait → SYS_NOTIFICATION_WAIT
  → 原 liteeth_interrupt → 原 liteeth_rx → netif_rx
  → Rust 上层取得完整 L2 帧
  → Driver::liteeth_start_xmit → 原 liteeth_start_xmit → 设备 SRAM / CSR
  → stop → reopen → remove → devm 回收 → 再 probe/remove
```

设备中断链为 QEMU NIC backend → LiteEth 模型 → GIC SPI 10 / INTID 42 → EL1 EOI 并暂时屏蔽 → Notification badge → EL0 调用原 C 中断函数 → 清设备 pending → `SYS_IRQ_ACK` 重开 SPI。这里没有 `sendto/sendmsg`，也没有硬件 IRQ 直接异步执行 C 回调。

## 兼容接口如何落到现有系统

| Linux 接口组 | 本次实现 | 使用的 exokernel 能力 |
| --- | --- | --- |
| platform / OF | EL0 解析 `litex,liteeth`、`reg-names`、slot 属性和中断号，生成独立配置 | 既有只读完整 DTB 交接 |
| devm / net_device | 单实例对象及托管资源表；probe 失败、remove 时撤销映射并释放堆对象 | 普通 EL0 堆；底层仍为既有 Frame 映射 |
| ioremap / LiteX CSR | PA 映射到固定 CPU VA；CSR 采用 32 位 volatile 事务和 AArch64 barrier | `MAP_MMIO` / `UNMAP_MMIO`，EL1 核对平台 grant |
| request_irq / free_irq | 保存 C 回调、绑定 Notification；解除绑定成功后才清回调与回收 | `NOTIFICATION_CREATE` / `IRQ_BIND` / `IRQ_UNBIND` / `NOTIFICATION_DESTROY` |
| skb / netif_rx | 线性报文分配；收包时移除以太网头的视图，但将完整 L2 帧复制给 Rust 上层；无论接收或丢弃都消费 skb | EL0 堆及固定单帧接收槽 |
| netif queue | stop/start/wake 状态；TX_BUSY 保持调用者报文所有权，等待完成 IRQ 后重试 | EL0 串行驱动任务 |
| stats / logging | 单所属线程统计；输出驱动实际使用的 `%d` 日志 | 当前使用 `SYS_PUTS`；限速计时直接读 EL0 counter |

**该 LiteEth 模式不使用 DMA。** 原驱动通过 `memcpy_toio/fromio` 复制设备 SRAM slot，随后通过 CSR 触发发送。其设备 SRAM 不是 CPU 普通 Frame，也没有可交给 DMA master 的主存地址。

为独立实验增加 `qemu-liteeth` 内核平台特性，仅授予 CSR PA `0x0b000000/0x1000`、SRAM PA `0x0b010000/0x2000` 与 INTID 42。正常 QEMU 与 Pi5 构建不增加这些授权，没有新增 syscall 或修改 BootInfo ABI。

## 运行

系统 QEMU 没有 LiteEth 模型。本仓库提供 `tools/liteeth/exo_liteeth.c` 和 virt 机器接入片段；它们通过真实 QEMU NIC backend 接入外部帧，并产生 GIC 电平中断。模型固定两个 RX / 两个 TX slot，验证 CSR、W1C、中断、忙状态和报文数据路径，不是完整 FPGA、PHY 或线速时序模型。

先取得 QEMU **10.2.1** 官方源码并解压到独立目录，再执行：

```sh
python3 tools/liteeth/build_qemu.py --source /path/to/qemu-10.2.1 --build /path/to/qemu-liteeth-build
python3 tools/liteeth/test_adapter.py
python3 scripts/test_liteeth.py --qemu /path/to/qemu-liteeth-build/qemu-system-aarch64
```

`test_liteeth.py` 自动构建 `LIBOS_APP=liteeth-smoke`，启动 ARM64 TCG、四核、UEFI 固件及独立测试盘，外部注入 17 帧并逐字节核对回显。当前测试覆盖 18、60、64、127、512、1024、1514、2048 字节长度，多个 RX/TX slot、重复 IRQ，以及 stop/reopen/remove/reprobe。结果及日志保存于 `target/liteeth-tests/`，不纳入源码。

Linux / Windows 宿主也应运行 ARM64 QEMU TCG；测试脚本的默认固件路径来自当前 macOS 环境，其他宿主通过 `--code`、`--vars` 指定现有 AArch64 UEFI 固件。本次不承担跨宿主脚本适配。

## 验证范围与下一步

兼容层宿主测试使用 ASan/UBSan，检查托管分配和映射失败回滚、TX_BUSY 不泄漏、TX slot 轮换、RX 数据复制、超长帧统计，以及启停/解绑/重探测。它使用普通数组，不能替代真实设备的 volatile、W1C、中断验证；这些由 QEMU 端到端测试覆盖。

当前设计只允许单实例、单所属 EL0 线程串行调用；没有 Linux 多核网络栈的 per-CPU、softirq、RCU 语义。原驱动通过 `netif_rx` 交给上层的帧被送入一个有界接收槽，槽满明确丢弃。MMIO 越界会明确终止任务，不降级为普通内存访问。

QEMU 通过只能证明本测试模型下的移植链路；真实 LiteX 板卡的 DTB、总线属性、PHY、FPGA 配置与缓存/顺序仍须独立验证。要让 `ping`、`sendto/sendmsg` 可用，下一步是在该 L2 接口上接入 ARP/IP/ICMP，再考虑 UDP/TCP 和 socket API；这些不是 LiteEth C 驱动本身提供的功能。

## 本机实际验收记录（2026-10-23）

- ARM64 QEMU TCG 中原 C 驱动完成 17 帧收发，外部逐字节匹配全部通过；串口日志出现 `LITEETH_READER_READY not ready`，实际覆盖 TX_BUSY 等待中断重试。
- 驱动核对首轮 16 帧的包数、字节数及零 RX/TX 错误，随后完成 stop/reopen、再收发一帧、remove/reprobe/remove，EL0 退出码为 0，EL1 完成资源回收。
- ASan/UBSan 兼容层测试通过；既有 `process` 和 `firmware-dtb` 两项 QEMU 回归通过。
- 原始帧结果与串口日志：`target/liteeth-tests/20261023-105948/`（完整自动构建入口复验通过；首轮为 `20261023-105852`）；既有回归报告：`target/dtb-regression/20261023-105702/`。这些是本机生成物，不随源码提交。
